# BLK-003 — BE-008's contract-runner AC lives in another lane

## Question

`TMU-BE-008` (lane `be`) has an acceptance criterion ("`run-contract.mjs` boots the real
app; Schemathesis coverage/fuzz phases report zero warnings for wired routes") that
requires editing `tests/contract/run-contract.mjs`. That path sits under `tests/**`,
which belongs to the **qa** lane in `.agent/lanes.json`; `_common` does not cover it
either. A `agent/be/TMU-BE-008-*` branch touching it fails `scripts/check-lane.sh`, so
AC #4 (`pnpm gate:full` green) is unsatisfiable — DoR check #6 fails and the task must
not start. How should the work be routed: **split the task across lanes**, or **change
the lane map**?

## Evidence

- `.agent/lanes.json` — `be` = `apps/web/src/server/**`, `apps/web/src/app/api/**`,
  `apps/web/package.json`, `apps/worker/**`, `**/*.test.ts`; `qa` = `tests/**`;
  `_common` has no `tests/contract/**` entry. `tests/contract/run-contract.mjs` is an
  `.mjs` file, so even the be lane's `**/*.test.ts` glob misses it.
- `scripts/check-lane.sh` allows only `[...lanes[lane], ...lanes._common]` against
  `git diff --name-only` — the file would be flagged `Out-of-lane edits for lane be`.
- `tests/contract/**` was scaffolded by TMU-OPS-013 (lane `qa`, merged `8bdd600`) and has
  been maintained only from qa branches since.
- WF-LANES (`docs/05-workflow/10-parallel-lanes-and-ownership.md`) cross-lane rule 3:
  "Acceptance criteria must be satisfiable inside the task's lane. If a criterion needs
  another lane's file, it is a `deps` entry or an explicit follow-up task, never a hidden
  requirement on the branch." Rule 5: "If a task genuinely needs a file outside its lane,
  stop and file a blocker (the lane map may need an `ops` change, or the task must be
  split)." `.agent/lanes.json` itself is "edit only via an `ops` task".
- No `TMU-QA-*` task exists today, so there is no existing follow-up task this AC could
  have been leaning on; the split target must be filed fresh.

## Options

1. **Split the task (recommended).** Keep `TMU-BE-008` for the be-lane half only —
   `Idempotency-Key`/fingerprint middleware + BE-12 rate limiters + API-route wiring and
   their tests (AC #1, #2) — and file an explicit follow-up `TMU-QA-001` (lane `qa`,
   `deps: [TMU-BE-008]`) for AC #3–#4: point `tests/contract/run-contract.mjs` at the
   real Next handlers and clear the Schemathesis 404/405/422 warnings from
   `REV-TMU-CTR-007`/`REV-TMU-CTR-008`, then run `pnpm gate:full` with the fuzz phase.
   Matches WF-LANES rule 3 exactly and keeps each file with its owning lane/agent.
2. **Change the lane map via an `ops` task.** A `TMU-OPS-*` branch adds
   `tests/contract/**` (or the single file) to the `be` lane in `.agent/lanes.json`, so
   one task stays whole. Cost: the contract-test harness permanently leaves qa
   ownership, and WF-LANES says lane-map edits are ops-only — two tasks (ops + be)
   serialised instead of one.
3. **Reassign the whole task to the `qa` lane.** Just moves the conflict: the middleware
   half touches `apps/web/src/server/**` (be lane). Not viable.

## Recommended default

**Option 1 (split).** It needs no governance change, follows the written cross-lane rule,
and mirrors how BE-007/BE-006 kept their test changes inside the be lane. The follow-up
QA task can own the Schemathesis work end-to-end (including any contract-doc updates the
warnings imply).

## What is ready when unblocked

- The be half (middleware/limiter work) is untouched and can start immediately after the
  task file is rewritten to drop `tests/contract/run-contract.mjs` from its expected
  files and AC #3–#4; `deps: [TMU-BE-007]` is already `DONE` (`717039c`).
- The qa half needs only the new task file (meta/`_common` paths are editable by every
  lane; creating the task is bookkeeping, the work itself runs on a `qa` branch).
