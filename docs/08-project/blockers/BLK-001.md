# BLK-001 — Dev DATABASE_URL rejects connections (Render IP allowlist mismatch)

## Question

Every attempt to reach the dev Postgres (`temuunair-dev` / `dpg-daujgv5g1s2s73d65lgg-a`,
Render free, region singapore, status `available` / `not_suspended`) now fails with
`Connection terminated unexpectedly` — TCP connects, then the socket is closed before auth.
This makes the gate's `db:check` step (and any live test, including `tests/db/check-live.test.ts`
and the new `tests/db/migrations-core.test.ts`) fail for **every** lane, so the loop cannot
complete any task. What should be done to restore DB access?

## Evidence

- Symptom reproduced 2026-10-03: bare `new pg.Client({DATABASE_URL}).connect()` fails with
  "Connection terminated unexpectedly" both immediately and after a 60 s wait; `SHOW max_connections`
  never runs because the connection dies.
- The instance's IP allowlist is a single `/32`: `103.164.231.241` ("local dev machine").
- The dev machine's current public IP is `182.6.74.166` (`https://api.ipify.org`) — a different
  address. Render's allowlist proxy accepts the TCP handshake then terminates off-list IPs, which
  matches this exact failure signature.
- The DB **was** reachable earlier in the same session: the full gate ran green minutes ago
  (`db:check: ok`, 3 live `check-live` tests passed), and `migrations-core.test.ts` passed 5/5
  before the connection started failing. A dynamic (residential) IP changed mid-session.
- Secondary factor (not yet separable from the above): ~25 throwaway `tmu_*` scratch databases
  and several stuck backends were created by crash-looping debug probes during diagnosis;
  cleanup via `pg_terminate_backend`/`DROP DATABASE` could not be confirmed because the admin
  connection itself could no longer connect. The free Render tier's low connection/disk headroom
  may now compound the allowlist blockage.
- NOT a code fault: `drizzle-kit generate` on the new `packages/db/src/schema.ts` reports
  "No schema changes, nothing to migrate" (schema ↔ `0002_core.sql` ↔ `meta/0002_snapshot.json`
  are internally consistent), and `bash`-level checks (lint, typecheck, i18n, unit, ml, contracts)
  all pass. Only the live-DB gate steps are blocked.

## Options

1. **Update the allowlist to the current IP.** Add `182.6.74.166/32` (Render dashboard →
   `temuunair-dev` → Connections/IP Allow List). Fastest, but the dev IP is dynamic, so this
   will break again on the next DHCP/VPN change.
2. **Point `DATABASE_URL` at a local pgvector Postgres** via `infra/docker-compose.yml`
   (`pnpm db:up`-style) for db-lane and gate work, reserving the hosted instance for deploys.
   Matches the BE-11/check note that local/CI Postgres is the intended plaintext target.
3. **Widen the allowlist to the user's predictable range** (or the Render/office egress range)
   so short IP churn doesn't block the loop. Weaker security posture on a free instance.
4. **Rotate to a local DB only + drop the hosted dev instance** from the loop entirely until M9.

## Recommended default

**Option 2** (local pgvector container as the gate/`DATABASE_URL` target). It is stable against
IP churn, keeps the gate hermetic, and leaves the hosted instance untouched for preview deploys.
If a human prefers the hosted DB, then at minimum also perform Option 1 *and* clean the leftover
`tmu_*` scratch databases + stuck backends created during this session's diagnosis
(`SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname LIKE 'tmu_%';`
then `DROP DATABASE` each `tmu_*`), and consider adding the current IP as a stop-gap.
