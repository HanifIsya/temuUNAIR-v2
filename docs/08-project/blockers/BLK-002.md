# BLK-002 — `db:check` aborts inside `pushSchema` for a populated schema

## Question

`pnpm gate` (every lane, every task, forever) now fails at the `migrations check` step because
`packages/db/src/check.ts` exits non-zero **without ever printing a `db:check:` verdict**. The
process dies inside `drizzle-kit`'s `pushSchema(...)` introspection call, which calls
`process.exit(1)` (via `renderWithTask5`'s error path, `api.mjs:3439`) the instant its
`db.query` shim throws — so `runCheck`'s own try/catch never runs and no reason is surfaced.
This only happens now that `packages/db/src/schema.ts` contains real tables; through all of
M0/M2 it was the empty `export {}` stub, so the step was trivially green and the defect stayed
latent. How should the drift gate be fixed so it is non-interactive and reports its verdict?

## Evidence — the migration is NOT at fault

- `tests/db/migrations-core.test.ts` (my new TMU-DB-001 test) applies the real migration folder
  to a scratch pgvector DB and introspects it directly → **5/5 pass**.
- `drizzle-kit generate` against the current `schema.ts` + `0002_core.sql` + snapshot →
  **"No schema changes, nothing to migrate"** (snapshot-based differ agrees).
- `drizzle-kit push --force` CLI against the *migrated* local DB → **"No changes detected"**
  (introspection-based CLI also agrees there is zero drift).
- The only thing that fails is `check.ts`'s programmatic `pushSchema(schemaModule, drizzle(pool), ["public"])`.
  Inside drizzle-kit's own `pushSchema` export (api.js) the introspection runs through a
  `db.query` shim whose signature `(query, params)` **drops `params`** and calls
  `drizzleInstance.execute(sql.raw(query))`; it throws somewhere in that introspection, and
  `renderWithTask5` then hard-exits instead of propagating the error. **Unverified candidate**:
  the dropped `params` binding — the CLI `push` path uses a plain `pg` driver that *does* bind
  parameters and runs the identical introspection cleanly, so this is the most likely difference
  (needs a confirming test in TMU-OPS-035, not yet proven).
- The **same `pushSchema` code path via the `drizzle-kit push` CLI** (plain `pg` driver, non-TTY,
  `--force`) runs the identical introspection cleanly ("No changes detected" / applies statements) —
  so the throw is specific to the `drizzleInstance.execute` shim `check.ts` passes, strongly
  pointing at Option 2 (plain-`pg.Client` `db.query`) as the minimal fix.
- `db:check` did briefly return `db:check: ok` immediately after the local DB was switched on
  (before the working tree accumulated any experiments); re-verified now on a freshly restarted
  container with the committed tree and it returns exit 1 with the silent-abort signature.

## Options

1. **Fix `check.ts` to not rely on the interactive `pushSchema`.** Use the same non-interactive
   path the CLI `push` uses: `pgPushIntrospect` + `applyPgSnapshotsDiff`/`generateMigration`
   with stubbed resolvers (no TTY), or wrap the whole `pushSchema` call so a thrown error is
   caught by `runCheck` and printed as `db:check: failed: <reason>` instead of `process.exit`.
2. **Give `check.ts` a real connection instead of the `drizzle(pool)` `.execute` shim** — the
   throw is in how introspection results are returned through `drizzleInstance.execute`; a plain
   `pg.Client`-backed `db.query` (exactly what the CLI uses) may avoid it.
3. **Replace `pushSchema` drift detection** with a snapshot↔introspection comparison driven by
   `drizzle-kit`'s exported `generateMigration` (pure function, no prompts), keeping the same
   frozen interface `runCheck(options, deps)` and the 5 s-friendly worker split.

## Recommended default

**Option 1** (wrap/guard the `pushSchema` call so it cannot silently `process.exit`, and switch
its `db.query` shim to the plain-pg form of Option 2). This is an `ops`-lane change to
`packages/db/src/check.ts` + a `tests/db` red/green regression that fails specifically when
`schema.ts` is populated (the exact case TMU-DB-001 introduced). It should be its own
`TMU-OPS-*` task; TMU-DB-001 and every subsequent task's gate stay blocked until it lands.

## What TMU-DB-001 already provides

Branch `agent/db/TMU-DB-001-db-core-tables` carries the complete, self-consistent core-tables
work — `schema.ts` (users/Auth.js adapter/locations/drop_points), `0002_core.sql` + snapshot +
journal, and the passing introspection test. It needs no change from BLK-002's fix; once the
gate step is repaired, `pnpm gate` should go green and the task can complete its DoD.

## Resolution (filled when closed)

Resolved via `pnpm patch drizzle-kit@0.31.11` (task `TMU-OPS-035`):
- Root cause confirmed: line 75275 of `drizzle-kit/api.js` (and `api.mjs`) defines `db = { query: async (query, params) => { const res = await drizzleInstance.execute(sql.raw(query)); return res.rows; } }`. The internal shim received `params` but discarded it when calling `drizzleInstance.execute(sql.raw(query))`.
- When introspecting tables with composite primary keys (`cprimaryKey.length > 1`, i.e. `accounts` and `verification_tokens`), `fromDatabase` runs `SELECT conname AS primary_key FROM pg_constraint ... WHERE connamespace = $1::regnamespace AND pg_class.relname = $2` passing `[tableSchema, tableName]`. Because `params` was dropped, Postgres failed with `error: there is no parameter $1` (code 42P02), causing `renderWithTask5`'s catch to invoke `process.exit(1)`.
- Fixed via `patches/drizzle-kit@0.31.11.patch` to interpolate parameters into the query string when present.
- `db:check: ok` against local pgvector verified; `check-live` 3/3 passed; gate green. TMU-DB-001 unblocked.
